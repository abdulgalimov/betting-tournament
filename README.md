# Tournament API

Самостоятельный NestJS-проект одного бессрочного турнира. Приложение принимает
события ставок из RabbitMQ, атомарно начисляет очки в PostgreSQL и возвращает
топ-100 вместе с персональной позицией игрока. Зависимостей от другого проекта,
workspace-пакетов и общих исходников нет.

## Запуск

Закреплённый стенд: Node.js 26.13.1, pnpm 12.21.0, PostgreSQL 18.7,
RabbitMQ 4.4.1. Пароли в `.env.example` предназначены только для локального демо.
Для запуска нужен Docker Compose 2.30 или новее.

```sh
cp .env.example .env
pnpm install --frozen-lockfile
pnpm check
docker compose up --build -d
```

Compose собирает только этот каталог и поднимает PostgreSQL, RabbitMQ, одноразовую
миграцию, API и observability-стек. API доступен на `http://localhost:3000`, Grafana —
`http://localhost:3001` (учётные данные `GRAFANA_ADMIN_USER` и
`GRAFANA_ADMIN_PASSWORD` из `.env`). PostgreSQL доступен на порту 5432, RabbitMQ —
5672, панель брокера — `http://localhost:15672`. PostgreSQL в Compose настроен под
поток событий от многих игроков: `shared_buffers=1GB`, `wal_compression=lz4`,
`max_wal_size=4GB`; Docker должен выделять ему не меньше 1,5 ГБ памяти.

Grafana заранее настроена на Prometheus, Loki и Tempo. Prometheus собирает
OpenTelemetry-метрики HTTP и Node.js процесса; Alloy собирает логи контейнеров,
а трассировки HTTP, PostgreSQL и RabbitMQ отправляет в Tempo. Для поиска используйте
Grafana Explore: Prometheus для метрик, Loki для логов, Tempo для трассировок.
Метрики и OTLP-порты доступны только внутри Compose-сети, кроме локальных портов
4317/4318 для отправки телеметрии с хоста. Логи собираются через Docker socket.
Producer запускается отдельно и использует доступный ему URL того же брокера.
Не запускайте два PostgreSQL/RabbitMQ на одинаковых опубликованных портах.

Для разработки с зависимостями из Compose:

```sh
docker compose up -d postgres rabbitmq
pnpm build
pnpm db:migrate
pnpm dev
```

`pnpm start` запускает `dist/main.js` и читает локальный `.env`, если он существует.
Приложение слушает `PORT` (по умолчанию 3000). `DATABASE_URL`, `RABBITMQ_URL`,
`EXCHANGE_RATES` и `LOG_LEVEL` проверяются при запуске. Курсы — фиксированные
десятичные строки USD за единицу валюты в формате `USD=1;EUR=1.1`.

Обработка событий и HTTP используют разные пулы PostgreSQL. `DATABASE_MAX_POOL`
(по умолчанию 8) задаёт пул записи событий.
`DATABASE_HTTP_MAX_POOL` (8), `DATABASE_HTTP_STATEMENT_TIMEOUT_MS` (2000) и
`DATABASE_HTTP_CONNECTION_TIMEOUT_MS` (1000) задают пул лидерборда: при его
перегрузке API быстро отвечает 503, а обработка ставок продолжается.

Consumer пишет события пачками, одной транзакцией на пачку. `EVENT_BATCH_SIZE`
(по умолчанию 250) ограничивает размер пачки, `EVENT_BATCH_CONCURRENCY` (2) — число
одновременных пачек; оно не превышает `DATABASE_MAX_POOL`. Произведение этих двух
значений должно быть не больше 2000: каждое событие держит до двух advisory locks.
`RABBITMQ_PREFETCH` (по умолчанию 1000) должен вмещать несколько пачек, иначе они
получаются мелкими.

До запуска HTTP и consumer приложение читает настройки соединений PostgreSQL.
Сумма `DATABASE_MAX_POOL + DATABASE_HTTP_MAX_POOL` должна быть не больше
`max_connections - superuser_reserved_connections - reserved_connections`.
Если настройка `reserved_connections` отсутствует в версии PostgreSQL, она
считается равной нулю. Зарезервированные слоты исключаются из бюджета пулов даже
для роли, которой они доступны. При превышении запуск завершается с ошибкой,
содержащей размеры пулов, оба резерва и доступный лимит. Проверка относится к
одному экземпляру: при выборе размеров учитывай также другие экземпляры и клиентов.

Турнир пишет логи уровня `error` и выше. `LOG_LEVEL=fatal` оставляет только
критические ошибки, а `LOG_LEVEL=silent` отключает логи. Прежние значения
`warn`, `info`, `debug` и `trace` принимаются и применяются как `error`.

`pnpm build` собирает приложение через Rspack (`@rspack/core` и `@rspack/cli`
2.3.3) в ESM-файл `dist/main.js`. Отдельная точка входа `drizzle/migrate.ts`
собирается в `dist/migrate.js`; SQL и метаданные лежат в `drizzle/migrations/`.
Мигратор находит их по пути `../drizzle/migrations` относительно своего файла.
Зависимости остаются внешними и загружаются из `node_modules`.
`pnpm dev` пересобирает приложение через Rspack при изменениях и перезапускает
Node.js. Дочерний процесс приложения читает `.env` при каждом запуске и поднимает
OpenTelemetry exporter на порту 9464, если используются настройки из `.env.example`.
Prometheus в Docker Desktop собирает эти метрики с `host.docker.internal:9464`.
Гистограмма обработки появляется после первой обработанной доставки RabbitMQ.
Мигратор запускается явно через `pnpm db:migrate`.

Локальные импорты пишутся без расширений и завершающего `/index`, например
`./app.module` или `../contracts`; публичные API каталогов остаются в `index.ts`.
TypeScript использует `module: ESNext` и `moduleResolution: bundler`, а проверка
типов приложения и тестов выполняется отдельно через `pnpm typecheck`
(`tsc --noEmit`). Rspack сохраняет метаданные декораторов, необходимые NestJS.

## HTTP API и OpenAPI

- `GET /docs` — Swagger UI.
- `GET /openapi.json` — OpenAPI для генерации внешних клиентов.
- `GET /health/live` — liveness.
- `GET /health/ready` — readiness PostgreSQL и RabbitMQ.
- `GET /leaderboard` с `X-Player-Id` — `{ top, player }`: первые 100 игроков
  и персональная запись с полной позицией, либо `null`, если игрок ещё не набирал очки.
  Перегрузка пула чтения, таймаут запроса или недоступная БД возвращают 503.

```sh
curl -H 'X-Player-Id: alice' http://localhost:3000/leaderboard
curl http://localhost:3000/openapi.json
```

`X-Player-Id` — тестовый идентификатор, не механизм авторизации. Допускаются
1–128 ASCII-символов: буквы, цифры, `.`, `_`, `:`, `-`; первый символ — буква или
цифра. Некорректный или отсутствующий заголовок возвращает 400. Очки в ответе —
десятичные строки. Топ и персональная позиция читаются в одном снимке БД.

Внешний test-producer генерирует HTTP-клиент по URL этого `/openapi.json`.
Сборка и запуск API не требуют наличия producer или генерации его клиента.

## Протокол RabbitMQ

Exchange `bets` имеет тип `topic`. Routing keys: `bet.settled` и `bet.rollback`.
Очередь `tournament.bets` — durable quorum с лимитом 5 повторных доставок;
постоянные ошибки и исчерпанные повторы идут через `bets.dlx` в
`tournament.bets.dlq`. ACK отправляется только после успешного коммита.

Compose применяет политику `delivery-limit: -1` только к настроенной quorum DLQ
перед запуском приложения. Политика действует и на существующую очередь с
сообщениями. Во внешнем RabbitMQ добавьте `delivery-limit: -1` в политику этой
очереди перед запуском consumer. Для DLQ со стандартным именем в стандартном
vhost можно создать политику этой командой, если у очереди ещё нет политики.

```sh
rabbitmqctl set_policy --apply-to quorum_queues tournament-dlq-retention \
  '^tournament\.bets\.dlq$' '{"delivery-limit":-1}'
```

Если PostgreSQL недоступен, consumer возвращает сообщение в очередь через
`basic.nack` без задержки (на RabbitMQ ≥4.3 это не тратит повторную доставку),
отписывается и проверяет базу через 1, 2, 4 … 30 секунд;
readiness на это время отвечает 503. При `lock_timeout` (SQLSTATE `55P03`)
подписка остаётся активной, а доставки затронутой пачки повторяются с задержкой
от 1 до 30 секунд в пределах лимита RabbitMQ. Ошибки данных (SQLSTATE `22`, `23`)
сразу уходят в DLQ. Consumer логирует код причины и метаданные доставки.

После устранения причины верните события командой `pnpm dlq:redrive --apply`
(в контейнере — `node dist/redrive-dlq.js --apply`). Без `--apply` команда показывает
размер DLQ. Redrive публикует непосредственно в `RABBITMQ_QUEUE` через default
exchange, переносит исходный тип события в AMQP-свойство `type` и удаляет
исходную копию после подтверждённой доставки в целевую очередь. Если очередь
отсутствует, сообщение остаётся в DLQ. Перед использованием нового CLI обновите
все consumer. Для CLI нужны права чтения DLQ и публикации в `amq.default`.

Тело события содержит ровно шесть полей:

```json
{
  "betId": "bet-1",
  "playerId": "alice",
  "currency": "USD",
  "stake": "5",
  "winAmount": "10.123456",
  "settledAt": "2026-11-18T12:00:00.123456Z"
}
```

`stake` и `winAmount` — неотрицательные десятичные строки до 18 целых и 6 дробных
знаков. Валюта — три заглавные ASCII-буквы и должна присутствовать в конфигурации
курсов. `settledAt` — фактическое время расчёта ставки с часовым поясом и не более
6 знаков дробной секунды. Числа с плавающей точкой не используются.

Повторная доставка идемпотентна. Rollback окончателен, включая доставку до
settlement; списывается сохранённый вклад. События одной ставки сериализуются в
PostgreSQL, а ставка и баланс обновляются в одной транзакции. Несовпадающий
`playerId` и конфликтующий settlement отвергаются.

Рейтинг сортируется по очкам убывающе, затем по времени достижения текущей суммы
возрастающе, затем по `playerId COLLATE "C"`. Время достижения — максимальный
`settledAt` активных ставок с положительным вкладом. Нулевой вклад время не меняет;
нулевой баланс имеет время `NULL`. Rollback пересчитывает время по оставшимся
ставкам. Порядок доставки на результат не влияет; микросекунды сохраняются.

## Проверки и миграции

```sh
pnpm check
pnpm test:integration
pnpm test:e2e
pnpm db:generate
pnpm db:migrate
pnpm dlq:redrive
```

Интеграционным тестам нужны `TEST_DATABASE_URL` и `TEST_RABBITMQ_URL`. Они создают
отдельные PostgreSQL-схемы и уникальные очереди, затем удаляют только свои ресурсы.
Используйте отдельную тестовую базу; пользовательские таблицы и очереди не очищаются.
HTTP E2E проверяют запущенный API (`TOURNAMENT_URL`, по умолчанию
`http://localhost:3000`) без producer. Межсервисные демо и E2E принадлежат отдельному
проекту test-producer. CI собирает локальный стенд и выполняет эти проверки.

SQL-миграции хранятся в `drizzle/migrations/`, журнал и снимки схемы — в
`drizzle/migrations/meta/`; применённые файлы не переписываются. Новая схема
требует новой миграции. CLI миграций находится в `drizzle/migrate.ts`, команда
`pnpm db:migrate` запускает собранный `dist/migrate.js`.
История технических решений сохранена в `DECISIONS.md`; старые ссылки на
монорепозиторий относятся к архитектуре до разделения.
